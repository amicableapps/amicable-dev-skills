# Adapt

Make this skill project-specific without editing its base files. The output is one file: `references/project.md` inside this skill. The base skill stays generic and update-safe; everything this project needs lives in the overlay.

Run when: the skill is first vendored into a repo, the stack or conventions change meaningfully, or the base skill noticed a gap (missing companion skill, unknown quality gates, ambiguous doc placement).

## Step 1: Detect, Don't Ask

Gather everything recoverable from the repo before asking the user anything:

- **Stack**: package manifests, lockfiles, framework config, backend/database layer, language, monorepo layout.
- **Feature placement**: where existing features live (`src/features/`, `app/`, `packages/*`, domain folders). Find two or three examples and name the actual pattern, not the aspirational one.
- **Docs conventions**: existing `docs/`, `_docs/`, ADR folders, RFC templates, wikis referenced from the README.
- **Quality gates**: real commands for typecheck, tests, lint, codegen — from package scripts, CI config, or contributor docs.
- **Context files**: `PRODUCT.md`, `DESIGN.md`, `AGENTS.md`, `CLAUDE.md`, README — note which exist and what they authoritatively answer.
- **Available skills**: list `.claude/skills/`, `.agents/skills/`, and user-level skill directories. Check specifically whether `impeccable` and `graphify` are present.
- **Graph output**: whether `graphify-out/GRAPH_REPORT.md` exists and is fresh.

## Step 2: Interview For What the Repo Cannot Answer

One batched round of questions, only for gaps:

- **Personas/actors**: who uses this product, and do any roles have different UX posture (e.g. mobile-first vs. dense desktop)?
- **Standing policies**: non-negotiables the plan must always respect (authorization model, compliance, branding anti-references, offline support).
- **Open decisions registry**: product/architecture questions that are deliberately unresolved. These must never be silently resolved by a plan.
- **Doc placement preference**: feature-adjacent packs, a central planning folder, or an external tool as source of truth.
- **Companion substitutes**: if `impeccable` is missing, what owns design direction here? If `graphify` is missing, how should large-codebase investigation start?

Skip any question the detection step already answered. Present findings as "here is what I detected, correct me" rather than an open-ended survey.

## Step 3: Write the Overlay

Write `references/project.md` in this skill's directory from the template below. Rules:

- Record only deltas from the base skill's generic defaults. If a base default already fits, leave it out.
- Every skill-routing entry must name a skill that actually exists in this repo's skill directories.
- Convert relative statements ("we're migrating to X") into dated facts.
- Re-runs replace the file; carry forward still-true entries, drop stale ones, and say what changed.

### project.md Template

```md
# Project Layer: <project name>

Generated by `feature-docs-builder adapt` on <YYYY-MM-DD>. Regenerate after stack or convention changes.

## Stack

- <language / framework / backend / database — one line each, only what affects planning>

## Personas

- <actor>: <posture, device, key expectation>

## Doc Placement

- Owned features: <e.g. `src/features/<name>/_docs/`>
- Pre-ownership planning: <e.g. `docs/features/<name>/` — temporary, move on implementation>

## Quality Gates

- Typecheck: `<command>`
- Tests: `<command>`
- Lint/other: `<command>`

## Skill Routing

- <local-skill-name>: use for <territory>. <Which lens it extends.>
- impeccable: <present | absent — substitute: ...>
- graphify: <present | absent — substitute: ...>

## Standing Policies

- <non-negotiable the plan must always respect>

## Open Decisions

- <deliberately unresolved question — plans must ask, never assume>
```

## Step 4: Verify

- Re-read the generated overlay as if you were a fresh session: does every entry either change behavior or answer a question the base skill would otherwise have to ask? Remove entries that do neither.
- Confirm every command in Quality Gates actually runs (or state that it was not executed and why).
- Report to the user: what was detected, what they decided, and what the overlay changes about future planning runs.
